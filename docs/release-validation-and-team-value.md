## 3. AgentTeams 到底带来什么：从底层结构看

### 3.1 结构事实（代码/文档依据）

- **队长 = 单会话编排者**：拆分任务、派发、接收报告、汇总；成员是持久的子会话（`src/members.ts`、`src/scheduler.ts`）。
- **固定协议**：队长 14 个团队工具、成员 4 个团队工具；创建/批准/继续/归档都不切换 system 与工具定义。见 [progressive-loading.md](./progressive-loading.md)。这保护了前缀缓存，避免“中途换提示词导致缓存读骤降”的反模式。
- **任务制调度**：每个 ready 任务原子 claim；依赖未满足不启动；失败的质量门禁不会解锁下游；成员一次只持有一个未完成 attempt（`src/scheduler.ts`、`src/state.ts`）。
- **持久化与恢复**：durable mailbox、attempt、团队状态文件；冷启动可恢复；重派/接管有明确规则。
- **质量门禁**：review/requirements 必须给 verdict；needs_revision/reject 必须失败并带 findings；实现/验证必须提交 acceptanceResults/commandsRun（`src/quality-gates.ts`）。
- **上下文隔离**：成员只拿固定成员规则 + persona + 自己的任务，不继承队长的完整对话。

### 3.2 Token 账：省在哪里，花在哪里

**省 token 的机制**

1. **上下文隔离**：独立的子任务不需要把队长的长对话再发一遍；成员从较小前缀开始。
2. **固定前缀/固定工具集**：同版本同配置下 system/tools 哈希稳定，缓存读能持续命中（文档明确要求）。
3. **任务契约即最小上下文**：成员只读任务相关文件，不需要整个仓库/整段讨论。
4. **成员工具更少**：成员只有 4 个团队工具，schema 占比更小。

**花 token 的机制**

1. 任务描述、成员 persona、报告、队长汇总、审查意见都是额外请求。
2. 每个成员都有自己的会话前缀；缓存前缀彼此独立，写入/命中率取决于调度节奏。
3. 审查/返工循环会增加轮次；耦合任务会在成员间来回确认。

**真实模型基准（历史记录，非本次重跑）**：`docs/agent-teams-real-model-verification.json` 的 3 成员并行只读评审案例：

| 轮次 | 请求数 | 耗时 | 未缓存输入 | 缓存读 | 输出 |
|---|---:|---:|---:|---:|---:|
| baseline fresh | 72 | 119.2s | 85,810 | 1,609,216 | 55,511 |
| final candidate | 65 | 101.2s | 78,710 | 1,125,120 | 52,103 |
| 旧团队冷恢复 | 19 | 26.8s | 44,012 | 516,352 | 6,478 |

读法：输入 token 的绝大多数是缓存读（baseline ≈95%），说明固定前缀在起作用；但这组数据是「多成员 vs 多成员」，**没有单 agent 对照组**，不能据此声称“比单 agent 省 token”。该 JSON 自己也把 “exact invoice or cost reduction” 列为 not proven。

**盈亏平衡（工程口径）**

设单个任务若由单 agent 完成需 `N` 步、每步重发上下文 `C`，团队拆成 `k` 个独立子任务、每个子任务上下文 `c_i`，协调开销 `O`（任务书 + 报告 + 汇总 + 审查）：

- 墙钟：团队 ≈ `max(T_i) + 协调`，单 agent ≈ `ΣT_i` → 独立任务越多、越并行，团队越快。
- token：团队 ≈ `Σ(c_i + work_i) + O`，单 agent ≈ `N·C` → 只有当 `Σc_i + O < N·C` 时才省；共享大上下文、子任务差异大时容易成立，小任务/高耦合时通常更贵。

### 3.3 交付效果

- **证据支持**：真实模型基准完成了三份独立评审、成员真实写文件、任务完成、队长汇总；冷恢复可继续旧团队。质量门禁与独立 verifier/reviewer 把“做完了”变成“可验证地做对了”。
- **代价**：协调与审查增加轮次；任务契约写不好时，返工成本高于单 agent。
- **结论**：AgentTeams 的价值不是“更便宜”，而是 **可并行的墙钟收益 + 独立验证带来的交付确定性**。token 是否下降取决于任务可拆分度与缓存命中，不能作为默认承诺。

### 3.4 适用/不适用

| 适合 | 不适合 |
|---|---|
| 3+ 条独立工作流（前端/后端/测试/文档） | 一行改动、单文件小修 |
| 需要独立评审/验证的交付 | 强耦合、频繁互相改同一文件 |
| 长任务需要上下文隔离与冷恢复 | 任务契约无法写清、验收不可验证 |
| 研究/扫描/多方案对比 | 对延迟极敏感、只需一次问答 |

## 4. 发布建议

**必须补齐（发布前）**

1. 真实浏览器 smoke：6 面墙 + 底栏入口、宗门志滚动、二维码加载、反馈复制/弹窗、换装动效。
2. 打包产物安装到隔离 profile 冷启动 + 真实宿主路由验证。
3. 真实模型最小业务跑一遍（create → dispatch → verify → review → summarize）。

**Token / 效率的下一步实测**

用同一仓库、同一模型，跑 A/B：

- A：单 agent 完成任务；B：3 成员团队（实现/验证/审查）。
- 记录：未缓存输入、缓存读、输出、请求数、墙钟、验收通过率、返工轮次。
- 成功阈值建议：墙钟下降 ≥25%，总 token ≤1.3×单 agent，验收通过率不低于单 agent；连续 3 次取中位数。
- 按角色拆分 usage（队长 / 实现 / 审查），定位协调开销；再决定成员数与是否合并审查角色。

**产品层可做的实用增强**

1. 活动面板显示本次团队的 token/请求/墙钟与每角色占比（先把账算清）。
2. 任务契约模板强制 acceptance + verify（质量门禁已有，前置到派发）。
3. 审查角色默认一个，避免“多重审查”把省下的墙钟吃回去。
4. 调度器优先唤醒“依赖已满足且上下文最短”的成员，减少空转。
